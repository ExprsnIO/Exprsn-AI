How a run can start today

Exists in 1.4.0

  • Manual from the console or POST /api/workflows/:id/runs (agents:run)
  • An app's record trigger: created, updated, deleted, transitioned (runs as the trigger's owner)
  • An app's schedule trigger: five-field UTC cron on an entity
  • A plugin's declarative workflow action or brokered workflow call (runs as the installer, trigger plugin:<chain>)
  • A tool call from an agent run when the workflow is published as a tool; the agent awaits approvals
  • Chat, only for read-only workflow tools that need no confirmation

Not possible today

  • A catalogue event starting a workflow directly
  • A workflow starting another workflow
  • A plain cron schedule without an app entity
  • A message, post, file, group or channel event with its own trigger kind
  • A workflow notifying users, raising a flag or calling an external webhook from a step (HTTP steps reach private addresses only)

Decisions taken in Sprint 29

Recorded in Backlog-1.5.0.md

  • Custom roles are defined by the tenant only; workspaces reuse tenant roles.
  • Access reviews assign both the workspace admin (tenant admin for tenant-level roles) and the member's directory manager; the first decision stands; the admin alone when the manager attribute is empty.
  • Also decided the same day: PDS hosting opt-in per tenant on a platform subdomain; DAV app passwords allowed with a fresh MFA step-up and a DAV-only scope; a 500 GB import quota per tenant; licence exceptions by a new legal-review role.

Prototype conventions

  • All eleven B-34 boards were built in Sprint 29, not only the Sprint 29 live screens.
  • No design-state controls on the page; states live in the command palette and the smoke run.
  • Proposed step kinds appear dashed with a "1.5 proposal" pill and refuse to publish, so the board documents the gap instead of hiding it.
